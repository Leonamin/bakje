# 수집 작업 큐

링크 하나가 저장되기까지는 두 개의 대기열을 거친다. 브라우저가 서버에 닿지 못하면 **브라우저 대기열(outbox)**에 머물고, 서버에 닿으면 **서버 작업 큐(`job` 테이블)**에서 처리된다. → [결정 011](../decisions/011-resilient-capture-queue.md)

```
[붙여넣고 저장 / 직접 입력]
   │ 네트워크 실패(오프라인, Tailscale 꺼짐)
   ├──────────────► 브라우저 outbox (localStorage)
   │                  │ 앱을 열 때 · 화면 복귀 · online 이벤트
   │◄─────────────────┘
   ▼
/api/ingest ── 형식 검사 실패 ──► 거절(작업 안 만듦)
   ▼
job: pending ─► running ─► done
                  │
                  ├─ 삭제·형식 오류 ─────────────► failed
                  └─ 그 밖의 실패 ─► pending(재시도 대기) ─► … 5회째 ─► failed
```

## 서버 작업 큐 (`src/lib/queue.ts`)

- 작업은 `job` 테이블에 저장되고 Next 서버 프로세스 안의 큐가 동시에 최대 2개씩 처리한다. 브라우저를 닫아도 처리는 계속된다.
- 실행 중이거나 대기열에 들어간 작업 ID를 메모리에서 추적해(`inFlight`) 같은 작업이 두 번 동시에 실행되지 않게 한다. 이전에는 링크를 등록할 때마다 `running` 작업까지 다시 큐에 넣어 중복 실행될 수 있었다.

### 재시도

| 실패 종류 | 처리 |
|---|---|
| 링크 형식 오류(`parseUrl` 실패) | 바로 `failed` |
| 삭제되었거나 볼 수 없는 게시글(`runFetch`의 `deleted`) | 바로 `failed` |
| 공유 링크 해소 실패, 파싱 실패, Reddit 차단, 네트워크·타임아웃 예외 | 재시도 |

- 공유 링크 해소 실패를 재시도 대상으로 둔 이유: 같은 Threads 공유 링크가 한 번 실패한 뒤 다음 시도에서 성공한 기록이 있다.
- 재시도 간격은 시도 횟수 기준 1분 → 5분 → 30분 → 30분이고, 최대 5회다. 5회째도 실패하면 메시지 끝에 `(5회 시도)`를 붙여 `failed`로 끝낸다.
- 재시도를 기다리는 작업은 `state='pending'`에 `next_attempt_at`이 설정된 상태다. 메시지는 `재시도 대기 (n/5) · <오류>` 형식이다.
- 수집 화면은 재시도 대기 작업을 시계 아이콘과 "HH:MM 다시 시도"로 표시한다.

### 자동 재개

- `src/instrumentation.ts`가 서버 시작 시 `startQueue()`를 부른다.
- `startQueue()`는 재시작·배포로 끊긴 `running` 작업을 `pending`으로 되돌리고, 실행할 때가 된 작업을 큐에 넣은 뒤, 30초마다 같은 확인을 반복한다. 여러 번 불려도 한 번만 시작한다(`/api/ingest`에서도 안전망으로 부른다).

### 스키마

`job`에 `attempts`(시도 횟수)와 `next_attempt_at`(다음 시도 시각)을 추가했다. 이 저장소에는 마이그레이션 도구가 없어서, `db()`가 열릴 때 `PRAGMA table_info(job)`로 컬럼이 있는지 확인하고 없으면 `ALTER TABLE`로 추가한다. → [데이터 모델](./data-model.md)

## 브라우저 대기열 (`src/lib/outbox.ts`)

- 등록 요청이 **네트워크 오류**(`fetch`의 `TypeError`)로 실패하면 링크를 localStorage `archive.outbox`에 넣는다. HTTP 오류 응답은 서버가 읽고 거절한 것이므로 넣지 않는다.
- `OutboxSync`(`src/components/outbox-sync.tsx`)가 앱 전체에 붙어 있다. 어느 화면을 열든, 앱이 다시 보일 때(`visibilitychange`), `online` 이벤트 때 대기열을 한 번에 보낸다.
  - 4xx 응답이면 서버가 판단을 끝낸 것이므로 대기열에서 지운다.
  - 5xx 응답이나 네트워크 오류면 남겨 두고 다음 기회에 다시 보낸다.
- 같은 링크가 두 번 전송돼도 서버가 "이미 저장된 게시글"로 처리하므로 데이터가 중복되지 않는다.
- 수집 화면은 대기 중인 링크를 목록 맨 위에 구름 아이콘과 "전송 대기 · 연결되면 자동으로 보냅니다"로 보여준다.
- iOS Safari는 Background Sync를 지원하지 않는다. 앱이 닫혀 있는 동안에는 보내지 않고, 다음에 앱을 열 때 보낸다.

## 오프라인 수집 화면 (`public/sw.js`)

서비스 워커는 **수집 화면만 오프라인에서 열리게** 하는 최소 범위로 둔다.

| 요청 | 처리 |
|---|---|
| `/add` 화면 이동 | 네트워크 우선. 성공하면 사본을 캐시하고, 실패하면 캐시 사본을 쓴다. |
| 그 밖의 화면 이동 | 네트워크만 쓴다. 실패하면 `/add`로 보낸다(캐시가 있을 때). |
| `/_next/static/*` | 캐시 우선. 파일 이름에 해시가 있어 새 배포와 섞이지 않는다. |
| `/api/*`, 미디어, 다른 출처 | 건드리지 않는다. 그래야 오프라인 등록이 실패해서 outbox로 간다. |

- 설치할 때 `/add` HTML을 받아 그 안의 `/_next/static/` 경로를 모두 미리 캐시한다. 첫 방문 때는 서비스 워커가 생기기 전에 화면이 이미 로드되기 때문이다.
- 캐시를 비워야 할 때는 `sw.js`의 `VERSION`을 올린다. 활성화 시 이전 이름의 캐시를 지운다.
- 개발 서버에서는 등록하지 않는다. 수정할 때마다 청크 이름이 바뀌어서 캐시가 방해만 된다.
- 웹앱 매니페스트(`src/app/manifest.ts`)와 `apple-icon.png`를 둬서 홈 화면에 추가할 수 있다. iOS Safari 탭으로 쓰면 7일 동안 쓰지 않은 사이트의 저장소가 지워질 수 있으므로 홈 화면 앱으로 쓰는 것을 권장한다.

## 검증 (2026-10-25, 복사본 데이터)

- 서버 시작만으로 `running`에 멈춰 있던 작업이 복구되어 처리됨
- 없는 Threads 공유 링크: 1회 실패 → 재시도 대기(1/5, +1분) → 30초 주기 확인에서 2회차 자동 실행 → 대기(2/5, +5분)
- 시도 횟수를 4로 맞춘 뒤 5회째 실패 → `failed` + `(5회 시도)`
- 없는 X 게시글: 첫 시도에서 바로 `failed`(삭제)
- 브라우저 오프라인 설정에서 붙여넣고 저장 → outbox 저장 → `online` 이벤트로 자동 전송 → outbox 비워짐
- 프로덕션 빌드에서 서버를 내린 상태로 `/`를 열면 캐시된 `/add`로 이동하고 링크가 outbox에 들어감 → 서버를 올리고 앱을 다시 열면 자동 전송
- 브라우저 도구의 오프라인 설정(CDP)은 페이지에만 걸리고 서비스 워커 요청에는 걸리지 않았다. 서비스 워커는 서버를 실제로 내린 상태로 검증했다.
- iPhone 실기기(홈 화면 앱, Tailscale 꺼짐)는 미검증
