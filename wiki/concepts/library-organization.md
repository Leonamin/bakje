# 묶음 편집과 원본 폴더 정리

## 자료 관계를 먼저 관리한다

AI는 사용자가 정한 기준으로 자료를 묶고 박제가 관계를 보관한다. 디스크의 폴더 모양은 등록의 전제 조건이 아니다. 구성요소는 프롬프트·본문·참고·결과 등의 역할과 언어·순서를 가진다. 각 종류를 하나씩으로 제한하지 않는다.

`/items/[id]` → **자료 묶음 편집**에서 다음을 지원한다.

- 모든 구성요소의 역할·언어·순서 저장.
- 선택한 구성요소를 새 자료로 분리. 기존 자료에 하나 이상 남겨야 한다.
- 같은 저장소의 다른 자료를 현재 자료에 합치기. 출처 정보는 구성요소 메타데이터에 보존하고 이전 자료 주소는 합쳐진 자료로 연결한다.
- 최근 변경의 영향을 받은 자료가 수정되지 않았다면 해당 변경을 되돌리기.

자료 revision을 확인하고 사용자 수정 잠금을 설정한다. ID와 입력 해시를 그대로 유지하므로 기존 임베딩과 진행 중인 분석을 재사용한다. 다른 저장소끼리 합치기는 파일 접근 책임이 달라 지원하지 않는다. 한 자료는 구성요소 최대 500개, 한 번에 합칠 대상은 최대 20개다. 중간 구성요소를 분리한 뒤에도 순서를 다시 연속으로 매긴다.

## 원본 정리는 별도로 선택한다

상세의 **원본 폴더 정리**는 한 자료, `/library` 저장소의 같은 패널은 전체 등록 자료를 대상으로 한다. 전체 계획은 18,000건 이상도 지속 작업으로 작성한다. MCP에서 자료를 지정할 때는 요청당 최대 100개, 생략하면 저장소 전체다.

1. 정리할 하위 폴더를 지정하고 **변경 계획 만들기**를 누른다. 원본을 읽어 내용 해시와 크기를 확인하며 파일은 쓰지 않는다.
2. 파일별 원래 경로·변경 경로와 공유 파일의 영향을 확인한다. 경로는 100개씩 조회한다.
3. 쓰기 가능한 연결에서 확인창 체크 후 적용한다. 원본을 이동하고 카탈로그 경로를 갱신한다.
4. **원본 위치로 되돌리기**는 기록한 경로와 내용을 확인해 복원한다.

목적 경로는 `<하위 폴더>/plan-<계획 ID>/<자료 ID>-<제목>/<순서>-<역할>-<언어>-<구성요소 ID>.<확장자>`다. 인라인 텍스트는 별도 파일로 생성한다. 자료별 `item.json`과 작업 루트의 `items.jsonl`에 관계를 기록한다. 파일이 여러 자료에 공유되면 한 번만 이동하고 모든 참조 경로를 함께 갱신한다. 이 경우 매니페스트의 `path_base: "storage"`가 연결 루트 기준 경로를 지정한다.

등록되지 않은 파일과 이전 JSONL은 이동하지 않는다. 직접 수정한 자료는 이전 자동 스캔에서 보존하므로 예전 경로를 읽어 실패하거나 원래 묶음으로 되돌리지 않는다. 정리된 규격은 생성된 `items.jsonl`로 재등록할 수 있다.

## 중단·충돌·동시 실행

계획 상태는 `planning → ready → queued → applying → applied`, 되돌림은 `undo_queued → undoing → undone`이다. 실패는 `failed`와 `phase`, 오류 메시지를 기록하며 재시도는 해당 방향을 이어 간다. 파일 처리를 시작하기 전만 계획을 취소할 수 있다.

- 계획 시점과 현재 자료 버전이 다르면 적용을 거절한다. 적용 후 자료가 바뀌면 되돌리기도 거절한다.
- 원본·결과 내용 해시와 크기를 검사한다. 다른 파일이나 변경된 내용은 덮어쓰지 않는다. 원래 경로가 사용 중이어도 복구를 중단한다.
- 동일 파일 시스템은 배타적 hard-link 후 원본 unlink, 다른 파일 시스템이나 지원하지 않는 공유 폴더는 배타적 복사·해시 검증·fsync 후 원본 삭제를 사용한다.
- 파일별 `pending → started → done`, 복구 시 `undo_started → undone` 체크포인트와 실행 임대를 기록한다. 프로세스 재시작 후 만료된 임대를 재점유한다. 중단된 부분 복사는 온전한 소스와 정확한 바이트 접두어가 일치하는 작업 파일만 재생성한다.
- 생성 파일은 작업 전용 임시 경로에 쓰고 동기화한 뒤 게시한다. 목적 루트의 작업 토큰과 각 디렉터리의 심볼릭 링크 여부를 검사한다.
- 실행·복구 중에는 저장소 잠금으로 같은 저장소의 스캔·수정·신규 배경 분석을 대기시킨다. 다른 저장소와 SNS 수집은 계속된다. 진행 중 파일 이동의 DB 체크포인트 간격은 파일 조회의 대체 경로로 연결한다.
- 일부 파일을 바꾼 후 실패하면 잠금을 유지한다. 재시도 또는 되돌리기로 해결해야 스캔을 재개한다. 빈 작업 폴더는 남기며 사용자 파일이 들어 있을 수 있는 폴더를 재귀 삭제하지 않는다.

이는 프로세스 중단을 복구하는 기능이다. 전원 차단과 NAS별 파일 시스템 의미의 전체 조합, 원본을 외부 프로세스가 동시에 수정하는 상황은 실환경 검증하지 않았다. 실행 중 원본을 외부에서 정리하지 않는다.

## API와 MCP

- `GET/POST /api/library/structure`: 후보·변경 이력 조회, 역할/순서 변경, 분리, 합치기, 되돌리기.
- `GET /api/library/items/[id]`: 최신 revision·구성요소·변경 이력·원본 정리 잠금.
- `GET/POST /api/library/organization`: 계획 목록·경로 페이지·진행 상황, 계획 작성·적용·되돌리기·재시도·취소.
- MCP: `edit_library_components`, `split_library_item`, `merge_library_items`, `undo_library_structure`, `plan_library_organization`, `get_library_organization`, `control_library_organization`.

에이전트는 먼저 계획을 사용자에게 제시한다. 원본 이동과 되돌리기는 검토·승인 후 MCP `confirm: true`로 실행한다. 임베딩 중에도 묶음 편집을 사용할 수 있다. 물리적 정리 실행 중에만 해당 저장소의 작업을 대기시킨다.

## 운영 조건과 검증

OpenNana 운영 연결 `/library/opennana`는 읽기 전용이다. 묶음 편집과 계획 작성은 사용할 수 있다. 실제 원본 정리는 관리자가 해당 연결의 마운트를 쓰기 허용으로 변경하고 UID 1000의 파일 쓰기 권한을 제공해야 한다. 기능 배포만으로 마운트나 원본 파일을 바꾸지 않는다.

`pnpm test:library-management`는 임시 폴더에서 역할·순서·분리·합치기·되돌리기, revision 충돌, 임베딩 재사용, 읽기 전용 차단, 파일 충돌, 공유 참조, 매니페스트 재등록, 적용/복구의 부분 복사와 DB 체크포인트 중단, 심볼릭 링크 경로 제한을 확인한다. 기존 `pnpm test:library`도 통과했다.

로컬 프로덕션 서버에서 실제 화면의 역할 드롭다운·순서 저장·분리·합치기·되돌리기와 원본 정리 적용·복구를 임시 자료로 확인했다. 390px 화면의 가로 넘침과 네이티브 select는 없었다. MCP 25개 도구 목록, 새 도구 7개의 요청·응답과 원본 변경 확인 매개변수 차단을 확인했다. 캡처는 `/tmp/bakje-management-browser/`다.
