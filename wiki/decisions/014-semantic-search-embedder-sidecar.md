# 014. 의미 검색은 임베딩 사이드카와 하이브리드 순위로

## Context

trigram 키워드 검색은 질의에 나온 글자가 없는 글을 찾지 못한다. 외국어 글, 번역하지 않은 글, 다른 말로 쓴 글이 그렇다. 운영 PC는 CPU 16코어·램 26GB이고 NVIDIA GPU가 없다.

## Decision

- 모델은 `google/embeddinggemma-2`(Apache 2.0)를 CPU fp32, 256차원(MRL)으로 쓴다. 앱은 Node라서 Python 사이드카 `embedder`(`embedder/`)로 분리한다.
- 사이드카는 compose 네트워크 안에서만 열리고(`http://embedder:8000`), 모델을 상주시키며 요청을 직렬화한다. 오디오 인코더는 쓰지 않아 로드하지 않는다(`audio_config: None`). 램은 안정 시 약 2.9GB, 최대 약 3.2GB(오디오 포함 때는 4.1GB/5.1GB)였고 `mem_limit`은 여유를 두어 6GB다. 모델 캐시는 `/var/lib/bakje/models`.
- 글은 1500자 단위로 청킹해(최대 12청크) `embedding`에 float32 BLOB으로 저장한다. 벡터 DB 없이 질의 때 전부 읽어 코사인을 계산한다(개인 규모 전제).
- `rebuildSearch`가 `embed_state` 행을 지우면 글이 stale이 되고, 60초 주기 스윕이 사이드카를 불러 다시 임베딩한다. 사이드카가 죽어 있으면 다음 주기에 재시도한다.
- 이미지도 같은 모델·같은 공간에 넣는다. 이미지 파일(gif·영상은 포스터 프레임)을 sharp로 896px JPEG으로 줄여 `/embed-image`로 보내고, 벡터는 `media_embedding`에 둔다. 파일이 없거나 읽을 수 없으면 빈 벡터를 표식으로 저장해 재시도를 막는다. 한국어 질의 임베딩이 글 벡터·이미지 벡터와 같이 비교되어 글 단위 최고 점수가 된다.
- 검색은 키워드 순위와 의미 순위를 RRF로 합친다(`searchHybrid`). 코사인 0.70 미만은 버린다. 질의가 없거나 `EMBEDDER_URL`이 없거나 사이드카가 응답하지 않으면 기존 키워드 검색만 돈다.

## Consequences

- 운영 램이 약 4~5GB 상시 늘어난다. 사용자가 알고 받아들였다.
- 20건 시험에서 한국어 질의 10개가 1위 10/10이었고, 키워드로는 0건인 질의("한국어 음성 합성 오픈소스", "할로윈 의상 프롬프트")에서도 해당 글이 나왔다. 임계값 0.70은 이 표본에서 정한 값이라 글이 늘면 다시 봐야 한다.
- 긴 글은 앞 12청크(약 1.8만 자)만 임베딩한다.
- 이미지 검색 시험(운영 이미지·gif·영상 포스터 29장): "야자수 아래 흰 수영복"→15번 글, "할로윈 호박"→14번 글, "검은 스타킹"→1번 글이 1위였다. 텍스트-이미지 코사인은 텍스트-텍스트보다 낮아 0.6~0.75에 분포하고, 없는 대상("고양이")도 0.68까지 올라 임계값 근처에서 오탐이 가능하다. 영상은 첫 프레임 포스터만 쓴다(여러 프레임은 후속). 이미지 임베딩은 장당 약 2.3초(워밍업 포함)로, 백필 29장+글 20건이 78초 걸렸다.
- "고양이" 같은 질의에서 관련 없는 글이 섞여 나오는 오탐이 관찰되었다. 글이 늘면 임계값 0.70 조정을 검토한다.
- 검색 카드에 매칭 방식을 보인다: 질의어가 글에 있으면 표시 없음, 의미 검색으로만 걸렸으면 "내용이 비슷"(글 벡터) 또는 "이미지와 비슷"(이미지 벡터) 배지. 유사도 수치는 질의마다 기준이 달라(스타킹 1위 0.77, 고양이 1위 0.71) 일반 화면에 보이지 않고 `?debug=1`일 때만 배지 옆에 붙는다. 3단계 범위 표시는 근거 데이터가 쌓인 뒤로 미뤘다.
- 실제 사용(2026-10-26): "여자"·"스타킹"·"AI"·"포즈"는 기대대로였고 "고양이"처럼 없는 대상은 0.70~0.71 점수의 글이 섞였다. 0.72로 올리면 정답 일부(스타킹 19번 0.70, 할로윈 이미지 0.71)도 빠져 임계값은 유지했다.
- 필터(플랫폼 등)는 합친 결과에 SQL로 다시 적용한다.
