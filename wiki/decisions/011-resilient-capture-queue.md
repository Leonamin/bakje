# 011. 수집 작업 재시도와 오프라인 대기열

## Context

사용자가 기대하는 동작은 두 가지다.

1. 링크를 한 번 등록하면 웹페이지를 떠나도 서버가 알아서 처리하고, 실패하면 다시 시도한다.
2. 오프라인(또는 Tailscale이 꺼져 서버에 닿지 않는 상태)에서도 링크를 등록해 브라우저에 대기시키고, 연결된 뒤 앱을 열면 대기 중인 링크를 알아서 전송한다.

2026-10-25 기준 코드(`src/lib/queue.ts`)를 확인한 결과는 다음과 같다.

- 등록된 링크는 서버 DB `job` 테이블에 들어가고 서버 프로세스 안의 큐가 처리한다. 페이지를 떠나도 처리된다. **1의 앞부분은 이미 충족한다.**
- 실패하면 바로 `failed`로 끝난다. Reddit 차단이나 타임아웃 같은 일시적 실패도 재시도하지 않는다.
- 배포·재시작으로 끊긴 `pending`/`running` 작업은 다음 `/api/ingest` 요청이 와서 `resumeStuckJobs()`가 불릴 때까지 멈춰 있다.
- 브라우저 쪽 대기열과 서비스 워커는 없다. 오프라인에서 앱 주소를 열면 Safari 오류 페이지가 떠서 링크를 넣을 화면 자체가 없다.

플랫폼 제약:

- iOS Safari는 Background Sync API를 지원하지 않는다. 앱이 닫혀 있는 동안에는 대기열을 전송할 수 없고, 앱을 열었을 때 전송해야 한다. 사용자의 기대("접속하면 알아서 시도")와 일치한다.
- Safari 탭으로 쓰면 오래 쓰지 않은 사이트의 저장소가 지워질 수 있다(7일 정책). 홈 화면에 추가한 웹앱은 이 정책에서 제외된다.
- 서비스 워커는 HTTPS가 필요하다. 운영 주소가 tailnet HTTPS(`tailscale serve`)라 조건을 만족한다.

## Decision

위험이 낮은 순서로 3단계에 나눠 도입한다.

1. **서버 재시도와 자동 재개**
   - `job`에 시도 횟수와 다음 시도 시각을 추가한다.
   - 일시적 실패만 간격을 늘려 재시도한다. 기본값은 1분 → 5분 → 30분, 최대 5회다.
   - 다시 해도 소용없는 실패(지원하지 않는 형식, 삭제된 게시글, 공유 링크 해소 실패 등)는 바로 끝낸다.
   - 서버 시작 시와 주기적으로 대기·재시도 대상 작업을 확인해, 재시작 후에도 끊긴 작업이 이어지게 한다.
2. **브라우저 대기열과 자동 전송**
   - 서버로 보내지 못한 링크를 브라우저 저장소에 넣고 수집 화면에 "대기 중(오프라인)"으로 표시한다.
   - 페이지를 열 때와 `online` 이벤트 때 서버로 전송하고, 성공한 것만 지운다.
   - 같은 링크가 두 번 가도 서버가 "이미 저장된 게시글"로 처리하므로 중복 저장은 생기지 않는다.
3. **서비스 워커와 홈 화면 앱 설정**
   - 오프라인에서도 수집 화면이 열리도록 수집 화면과 정적 파일만 캐시한다. 캐시가 꼬여 새 배포가 반영되지 않는 위험을 줄이려고 범위를 좁게 잡는다.
   - 홈 화면 추가용 웹앱 매니페스트를 둔다.

## Consequences

- 1단계 후에는 일시적 실패가 사람 개입 없이 회복되고, 배포가 진행 중인 작업을 잃지 않는다.
- 2·3단계 후에는 오프라인이나 Tailscale이 꺼진 상태에서도 수집이 끊기지 않는다. 전송은 앱을 다시 열었을 때 일어난다.
- 홈 화면 앱으로 쓰는 것을 권장 사용 방식으로 둔다. Safari 탭에서는 대기열이 지워질 수 있다.
- 미확정·후속 확인:
  - 어떤 실패를 일시적으로 볼지는 구현하면서 현재 오류 메시지를 기준으로 분류한다.
  - 재시도 간격과 횟수는 기본값이며 운영하면서 조정한다.
  - iOS 홈 화면 앱의 오프라인 동작은 실기기에서 검증해야 한다.
