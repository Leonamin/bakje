# UX 사례 작성

문제 하나당 kind=ux 박제본(카드) 하나를 만든다. 같은 화면·같은 해결의 사례는 새로 만들지 않고 기존 카드에 합친다. 해결(또는 제안)까지 정리된 뒤에 등록한다.

## 카드 형식

- 제목: 문제를 한 문장으로 쓴다. 예: "이미지 업로드 안내에 지금 행동과 상관없는 내부 정책이 나옴"
- 제목 아래 한 줄: `제품 · 화면 · UX · **해결** (배포 단계)`. 상태는 해결 또는 제안이다.
- 본문은 아래 네 절만 쓴다.
  1. `## 문제`: 사용자가 겪은 일과 그 이유. 실제 관찰(사용자 질문, 오류)이 있으면 쓴다.
  2. `## 해결`: 바꾼 내용. 제안이면 제안한 내용.
  3. `## 원칙`: 다른 화면에도 쓸 규칙. 근거(예: 닐슨 휴리스틱) 이름을 굵게 쓰고 한 줄로 설명한다. 예외가 있으면 한 줄 추가한다.
  4. `## 다시 볼 때`: 이 카드를 꺼내 볼 작업 상황.
- 제외: PR, SHA, 테스트, 출처 JSON, 코드. 관찰과 해석, 제안과 검증 결과를 섞지 않는다. 없는 내용은 꾸미지 않는다.
- 원칙은 별도 문서로 만들지 않고 카드 안에 둔다.

## 등록

- external_id: `ux-card:v2:<slug>`. 폴더: `ux-cards-v2/<slug>`. 본문은 구성요소 key=doc, role=doc.
- tags: `ux`, 주제 태그 1~2개.
- metadata: `product`, `screen`, `area`, `status`. 이 카드가 대신하는 옛 카드가 있으면 `replaces`에 ID 목록을 적는다.
- 대체된 옛 카드는 `manage_library_items`의 hide로 정리한다.

## 첨부

- 이미지는 최대 10장, 보통 1~3장만 넣는다. 핵심 상태를 보여 주는 장면만 고른다. kind=image, role=screenshot 또는 result.
- 캡션에 각 이미지의 상태(Before, After, 환경)를 쓴다. 비교 단계가 다른 이미지를 전후 증거로 쓰지 않는다. 수정 전 화면이 없으면 캡션에 그 사실을 쓴다.
- 영상은 kind=video. 생성 이미지를 실제 캡처로 쓰지 않는다. APNG의 전체 동작을 박제가 분석한다고 가정하지 않는다.

## 수정과 이전

- 같은 사례의 후속 결과는 `patch_library_item`으로 doc이나 첨부 key만 바꾼다. 다른 근거는 보존한다.
- 기존 UX 저장소는 자동 삭제·일괄 이전하지 않는다. 이전 범위를 정하고 표본을 먼저 등록해 검색·수정·원자료 접근을 확인한다. 이전 전에는 기존 CLI·저장소를 유지한다.
